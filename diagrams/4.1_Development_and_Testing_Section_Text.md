## 4.1 Development and Testing

The system was developed following the Agile software development methodology
described in §3.1, in which the development is carried out in short iterations
and each iteration ends with a working part of the system that can be tested. The
testing reported in this section was therefore performed continuously while the
system was being developed rather than once at the end of the project, so that a
defect found in one iteration was corrected before the next iteration was built
on top of it.

Three levels of testing were performed. **Unit testing** verified each module of
the system on its own, in order to confirm that a single module produces the
expected behavior under both valid and invalid input. **Integration testing**
verified the modules together, in order to confirm that the data passed from one
module to another is correct and that the functions which depend on more than one
module, such as the validation of an appointment or the automatic marking of a
missed appointment, behave as a whole. **User acceptance testing** verified the
system against the needs of the three users of the clinic, the administrator, the
dentist and the patient, in order to confirm that each of them can complete the
work for which the system was built.

The system was tested on the deployment described in §3.3, which is a local web
server on a Windows workstation running Apache through XAMPP, PHP 8.2.12 and
MariaDB 10.4.32, accessed through a web browser. The database of the clinic was
created from the schema of the system, and the test data consisted of the clinic
settings, the dental services, the dentist schedules and the appointment records
used during the development and the demonstration of the system.

The results of the three levels of testing are presented in Tables 22, 23 and 24.
The acceptability of the system as perceived by the respondents through the
evaluation instrument described in §3.12 is reported separately in §4.2, where
the responses are tallied and interpreted against the software product quality

### 4.1.1 Unit Testing

Unit testing verified each module of the system on its own, before it was joined
to the other modules. Each module was given both valid and invalid input, so that
the test reports not only that the module works when it is used correctly but
also that it rejects the input it is supposed to reject, such as an incomplete
login form, an invalid e-mail address, a password that does not match the stored
hash, or a request for an administrator page made by a user who is not an
administrator. The modules verified at this level are the user authentication, the
user registration, the session management, the role-based access control, the
patient number generation, the queue number generation, the notification creation,
the output encoding and the database query handling of the system. The unit test
cases are presented in Table 22.

### 4.1.2 Integration Testing

Integration testing verified the modules of the system together, after the
individual modules had passed their unit tests. The purpose of this level was to
confirm that the data written by one module is read correctly by the module that
depends on it, and that a function which spans several modules completes as a
whole. The functions verified at this level include the registration of an account
and the signing in with that account, the booking of an appointment together with
the generation of the available starting times, the detection of an appointment
conflict, the saving of the appointment, the change of an appointment status
together with the creation of the notification that must follow it, the sending
of an appointment reminder through the e-mail service of the clinic, the automatic
marking of a missed appointment together with the notification to the patient, the
registration of a walk-in patient through the public QR form together with the
queue entry and the queue number, the submission of an appointment concern
together with the notification to the administrator, and the pipeline of the
demand forecast, which reads the appointment records, prepares the historical
dataset and produces the forecast. The integration test cases are presented in
Table 23.

### 4.1.3 User Acceptance Testing

of the clinic, in order to confirm that each of them can complete the tasks for
which the system was built. The acceptance criterion of each test case is stated
from the point of view of the user rather than from the point of view of the code:
a test case passes when the user is able to complete the task, without assistance,
using the functions of the role of that user. The three users who took part are
the administrator, the dentist and the patient of Abalos Dental Clinic, and the
same users are the respondents of the evaluation instrument described in §3.12,
whose responses are reported in §4.2 and interpreted against the software product

### How to fill the Actual Result and Status columns (not for submission)

The two columns were left blank on purpose. Fill them by running each test case
against the running system and then writing what you actually observed:

1. Start Apache and MySQL from the XAMPP control panel, and open the system at
   `http://localhost/dental-ai-system-fixed/login.php`.
2. Run the test case exactly as the Test Condition states. Where the condition
   needs an account, a dentist schedule, a dental service or an appointment record,
   prepare that record first.
3. In **Actual Result**, write what the system did, in the same style as the
   Expected Behavior, for example "The system displayed 'Please enter your email
   and password.' and no session was created."
4. In **Status**, keep the tick that matches what happened and delete the other,
   so the row reads `[✓] Passed  [ ] Failed` or `[ ] Passed  [✓] Failed`.
5. If a test case fails, record the failure and correct the module, then run the
   test case again and record the corrected result. A failed test case that was
   corrected is worth reporting, because it shows that the testing found
   something; a table in which every row passed on the first run is more difficult
   to defend before a panel.

The two e-mail test cases, TC022 and TC025, depend on the SMTP account configured
in `config.php`. If the workstation where the defense is held has no connection
to that account, run those two test cases on the machine where the system was
developed, or record the outcome of the sending that the system reports, which is
what the test case states.
