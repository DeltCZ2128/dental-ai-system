## 4.1 Development and Testing

The system was developed following the Agile software development methodology
described in Â§3.1, in which the development is carried out in short iterations
and each iteration ends with a working part of the system that can be tested. The
testing reported in this section was therefore performed while the system was
being built rather than once at the end of the project, so that a defect found in
one iteration was corrected before the next iteration was built on top of it.

Two levels of testing are reported here, and they are presented in one table
because the administrator functions of the system were tested together as they
were completed. **Unit testing** verified each admin module on its own, in order
to confirm that the module produces the expected behavior under both valid and
invalid input, such as a login form that is left incomplete, a password that does
not match the stored password, a request for an admin page made by a user who is
not an administrator, an appointment booked on a Sunday, an appointment booked on
a rest day of the dentist, an appointment that overlaps another appointment, or a
status value that is not one of the statuses the system allows. **Integration
testing** verified the admin modules together, in order to confirm that the record
written by one module is read correctly by the module that depends on it, and that
a function which spans several modules completes as a whole, such as the saving of
an appointment together with the validation that guards it, the change of an
appointment status together with the notification that must follow it, the
registration of a walk-in patient together with the queue entry and the queue
number, and the pipeline of the demand forecast, which reads the appointment
records, prepares the historical dataset and produces the forecast.

The system was tested on the deployment described in Â§3.3, which is a local web
server on a Windows workstation running Apache through XAMPP, PHP 8.2.12 and
MariaDB 10.4.32, accessed through a web browser. The database was created from the
schema of the system, and the test data consisted of the clinic settings, the
dental services, the dentist schedules and the appointment records used while the

### How to fill the Actual Result and Status columns (not for submission)

The two columns were left blank on purpose, because the result of a test can only
be written by running the test. To fill them:

1. Start **Apache** and **MySQL** from the XAMPP control panel, then open the
   system at `http://localhost/dental-ai-system-fixed/login.php`.
2. Prepare the data the test case needs before running it. Most cases need a
   dentist with a saved schedule, at least one dental service, and a patient
   record. TC007 to TC009 need a Sunday in the calendar and a dentist with a saved
   rest day and a saved day-off. TC028 and TC029 need appointment records spread
   over several days.
3. Run the test case exactly as the Test Condition states. Use the invalid input
   for the invalid cases, for example by submitting the appointment form on a
   Sunday for TC007.
4. In **Actual Result**, write what the system actually did, in one or two
   sentences and in the same style as the Expected Behavior. For example, for
   TC007 write: "The system displayed 'The clinic is closed on Sunday. Please
   choose another date.' and no appointment was created."
5. In **Status**, keep the tick that matches what happened and delete the other, so
   that the row reads either `[âœ“] Passed  [ ] Failed` or
   `[ ] Passed  [âœ“] Failed`.
6. If a test case fails, correct the module, run the test case again, and record
   the corrected result. A test case that failed and was then corrected is worth
   reporting, because it shows that the testing found something; a table in which
   every row passed on the first attempt is harder to defend before a panel.

Two cases depend on the mail account of the clinic. **TC014**, **TC015** and
**TC038** use the email service configured in `config.php`. If the workstation
where the defense is held has no connection to that account, run these three cases
on the machine where the system was developed, or record the outcome that the
system itself reports, which is what the Expected Behavior states.
